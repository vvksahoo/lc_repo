IP Addresses

Foundation

An IP address is the internet's postal system. Every device needs one for data (packets) to be delivered correctly. Think of it as a home address — without it, nobody knows where to send your mail.

Private vs Public IP

Private IP

  • Internal to your home/office network
  • Ranges: 192.168.x.x, 10.x.x.x
  • Assigned by your router via DHCP
  • Not reachable from the internet
  • Multiple devices share one public IP

Public IP

  • Globally unique, visible on the internet
  • Assigned by your ISP or cloud provider
  • Your router's outward-facing address
  • What servers use to reach you
  • Servers use static (fixed) public IPs

NAT — Network Address Translation

Your router uses NAT to allow multiple devices (laptop, phone, TV) to share a single public IP. It tracks which device made which request and routes the response back correctly. The internet only sees your router's public IP — never your device's private IP.

System Design Insight

Servers you deploy on AWS/GCP get a public IP. Your application must listen on that IP and a port (e.g. 0.0.0.0:8080) to receive traffic. Use Elastic IPs (AWS) or Reserved IPs (GCP) for production — they don't change even if you replace the underlying instance.

DNS — Domain Name System

Foundation

DNS translates human-readable names like google.com into IP addresses machines understand. Without DNS you'd memorise 142.250.80.46 instead of typing google.com. It is the internet's phone book.

The DNS Resolution Journey

When you type google.com, a chain of lookups happens before your browser can connect. Each layer is checked in order — the full journey only happens on a complete cache miss.

1
Browser DNS cache — checked first. Returns instantly if found.
↓ miss
2
OS cache + hosts file — /etc/hosts overrides take precedence here.
↓ miss
3
Recursive resolver — your ISP, or 8.8.8.8 (Google) / 1.1.1.1 (Cloudflare). Does the full legwork.
↓ asks root
4
Root nameserver — 13 clusters (A–M), 1,800+ physical servers via anycast. Knows who manages .com.
↓ asks TLD
5
TLD nameserver — manages .com, .org, .in. Knows which nameserver holds google.com.
↓ asks authoritative
6
Authoritative nameserver — Google's own DNS. Returns the final IP: 142.250.80.46. Answer is cached by all layers.

Common DNS Record Types

RecordMapsUse case
ADomain → IPv4Point mysite.com to 1.2.3.4
AAAADomain → IPv6Same as A but for IPv6
CNAMEAlias → domainPoint www to mysite.com, or domain to ALB DNS name
MXDomain → mail serverEmail routing for your domain
TXTDomain → text stringSSL verification, email authentication (SPF/DKIM)
NSDomain → nameserverDelegates your domain to a DNS provider
TTL—How long resolvers cache the answer (seconds)
TTL Migration Strategy

Before a server migration: lower TTL to 60 seconds and wait for current TTL to expire. During: update the A record. Users pick up the change within 60 seconds. After migration is stable: raise TTL back to 3600–86400 for performance.

DNS Caching

Foundation

DNS results are cached at four separate layers. The full DNS resolution chain only runs on a complete miss at all four layers. For returning visitors, DNS is almost always served from cache.

Browser cache
Checked first. Lives in memory — gone when you close the browser. Chrome caps max TTL at ~60s regardless of the DNS record.
TTL: 1s – 60s
OS cache
Survives browser restart. /etc/hosts file here can override any DNS record. Respects DNS TTL.
TTL: respects DNS
Router cache
Shared across all devices on your network. Runs dnsmasq on most consumer routers. Lives in RAM — cleared on reboot.
TTL: minutes
ISP recursive resolver
Shared across thousands of ISP customers. Very high hit rate on popular domains. TTL set by the domain owner.
TTL: set by domain owner

Browser TTL Behaviour by Browser

BrowserMax cached TTLNote
Chrome~60 secondsInspect at chrome://net-internals/#dns
Firefox60 secondsConfigurable via about:config → network.dnsCacheExpiration
Safari~10 minutesCaps higher than Chrome/Firefox

How to Flush DNS

# macOS
sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder

# Windows
ipconfig /flushdns

# Linux (systemd)
sudo systemd-resolve --flush-caches

# Router (dnsmasq)
killall -HUP dnsmasq

# Chrome
chrome://net-internals/#dns  → Clear host cache
Debugging Tip

When testing a DNS migration from home, all your devices share the same router cache. Flushing just your laptop's OS cache won't help if the router still has the old IP cached. Always flush or reboot the router too, or test from a mobile network.

DNS Providers & Resolvers

Infrastructure

DNS Authority Hierarchy

The internet's DNS system is a strict hierarchy. ICANN governs the root, delegates authority to TLD registries, who delegate to authoritative nameservers that you control.

ICANN
Governs the entire DNS system. Delegates TLD management to registries (Verisign, PIR, Google, Amazon).
1 authority
Root nameservers
13 identities (A–M), operated by 12 organisations including Verisign, NASA, ICANN, Cogent. 1,800+ physical machines worldwide via anycast.
1,800+ servers
TLD nameservers
~1,500 TLDs. Verisign manages .com and .net. PIR manages .org. NIXI manages .in. Each TLD has multiple redundant servers.
~1,500 TLDs
Authoritative nameservers
Your DNS provider. Holds your actual A/CNAME/MX records. Cloudflare, Route53, GoDaddy, Namecheap, Google Cloud DNS. You choose this when registering a domain.
You control this

Anycast — How the Closest Server Answers You

Cloudflare, Google, and all root/TLD servers use anycast routing. The same IP address (e.g. 1.1.1.1) is announced from 300+ physical locations simultaneously. Internet routers automatically send your query to the nearest physical machine. You never choose — the network chooses based on routing distance.

This means when you're in Chennai querying 1.1.1.1, you're hitting a server in Mumbai or Singapore — not the US. That's why DNS feels instantaneous despite global infrastructure.

Scale Reference

Cloudflare: 300+ anycast locations · Google: 200+ locations · AWS Route53: 100+ edge locations. The .com TLD alone runs 13 nameservers labeled a.gtld-servers.net through m.gtld-servers.net.

Domain Registration & DNS Setup

Infrastructure

There are two distinct roles that are often confused: the registrar (where you buy the domain) and the DNS provider (where you manage records). They can be the same company or different ones.

Step-by-Step: Getting Your Domain Resolving

Step 1 Buy the domain from a registrar

GoDaddy, Namecheap, Google Domains, Porkbun. The registrar notifies the TLD registry (e.g. Verisign for .com) that you own this domain. Your domain is now in the global registry.

Step 2 Point nameservers to your DNS provider

In your registrar's panel, set the NS records to your DNS provider. E.g. ns1.cloudflare.com, ns2.cloudflare.com. This tells the TLD registry which server holds your records.

Step 3 Create DNS records in your DNS provider

Add an A record: mysite.com → 54.1.2.3 (your load balancer IP). Add CNAME, MX, TXT records as needed. On AWS, use an Alias record pointing to the ALB DNS name.

Step 4 Wait for propagation

DNS changes propagate based on TTL. With a TTL of 3600, it can take up to an hour for the world to see your new record. Lower TTL before changes, raise it after.

DNS IP — Which IP Goes in the A Record?

Always point DNS to the load balancer IP — never to individual service instances. Service instances are ephemeral — they scale up and down, restart, and get replaced. Their IPs change constantly. The load balancer has a stable, permanent IP that never changes.

LayerWhat IP you configureChanges?
DNS A recordLoad balancer IP or DNS nameAlmost never
LB target groupPrivate IPs of service instancesConstantly — auto-scaling
Service instanceAssigned by cloud, ephemeralEvery time it restarts
AWS Specifics

AWS ALBs get a DNS name like myapp-123456.ap-south-1.elb.amazonaws.com, not a raw IP. Your Route53 A record uses an Alias record pointing to this DNS name. AWS manages the underlying IPs internally. This is the standard pattern on AWS.

Proxy vs Reverse Proxy

Infrastructure

The key difference in one sentence: a forward proxy hides the client. A reverse proxy hides the server.

Forward proxy (client-side)

Server sees the proxy's IP, not your real IP.

  • Anonymity and privacy (VPN-like)
  • Bypass geo-restrictions
  • Corporate content filtering (block social media)
  • ISP-level caching of shared resources

Reverse proxy (server-side)

Client sees one IP; behind it can be 5,000 servers.

  • Load balancing across backend servers
  • SSL/TLS termination (HTTPS → HTTP internally)
  • DDoS protection and rate limiting
  • Response caching (serve cached HTML/images)
  • Request compression
  • Path-based routing (/api → service A, /static → CDN)

When to Use Which

ScenarioUse
Corporate office blocking social mediaForward proxy
Anonymous browsing / privacyForward proxy (VPN)
Deploy multiple backend servers behind one domainReverse proxy
Manage SSL certificates in one place onlyReverse proxy
Protect servers from DDoSReverse proxy
Cache API responses at the edgeReverse proxy / CDN
Real World

When you open Netflix, you're hitting a reverse proxy (Cloudflare or AWS CloudFront). You have no idea whether 5 or 5,000 servers are behind it — and that's exactly the point. Engineers can add or remove servers without you ever noticing.

Load Balancer

Infrastructure

A load balancer distributes incoming traffic across multiple backend instances. Its superpower over DNS load balancing is active health checks — it probes every backend every 5–30 seconds, and instantly removes unhealthy instances from the pool without any DNS propagation delay.

Layer 4 vs Layer 7

Layer 4 — Transport level

  • Routes by IP address + port only
  • Cannot see HTTP headers or URL path
  • Very fast — minimal processing
  • Good for: raw TCP, non-HTTP traffic
  • Example: AWS NLB, HAProxy (TCP mode)

Layer 7 — Application level

  • Reads HTTP headers, URL path, cookies
  • Route /api to service A, /static to CDN
  • SSL termination, WebSocket upgrades
  • Good for: all HTTP/HTTPS microservice traffic
  • Example: AWS ALB, Nginx, Cloudflare, Traefik

The Full Request Stack

DNS (Route53)
Resolves myapp.com to the load balancer IP. Static — never changes. TTL can be high.
One IP, permanent
Load balancer
Distributes traffic across nodes. Health checks. Stable IP / DNS name. Spans multiple AZs.
AWS ALB · GCP LB
Reverse proxy / API GW
SSL termination, caching, path routing, auth, rate limiting. Runs on each node or as a dedicated tier.
Nginx · Kong · Envoy
Service instances
Ephemeral — scale up/down freely. Private IPs only. Register with LB on startup, deregister on shutdown.
EC2 · Containers · Lambda

Scale Up / Down — What Actually Happens

Scale UP (traffic spike)

  • Auto-scaler launches new instance
  • Instance starts, runs health check
  • Registers itself with the LB
  • LB now routes to it — instant
  • DNS record: unchanged

Scale DOWN (traffic drops)

  • Auto-scaler marks instance for removal
  • LB stops sending new requests (draining)
  • Existing connections finish gracefully
  • Instance deregisters, then terminates
  • DNS record: unchanged

Load Balancing Algorithms

Infrastructure

Round Robin

1 → 2 → 3 → 1 → 2 → 3

Requests distributed to each server in sequence equally.

Use when: identical server hardware
⚠ Ignores server load — slow server still gets requests

Weighted Round Robin

A(3×) → B(1×) by weight

Servers get requests proportional to their assigned weight.

Use when: mixed hardware capacity
✓ Also great for canary deploys — send 5% to new version

Least Connections

route → server with fewest open connections

Tracks active connections and always routes to the least busy server.

Use when: requests vary in processing time
✓ Best for WebSockets, streaming, ML inference APIs

IP Hash (Sticky Sessions)

hash(client IP) → always same server

Same client always hits the same backend server.

Use when: server stores session state locally
⚠ Avoid this pattern — store sessions in Redis instead

Random with Health Check

random healthy server

Pick any healthy server at random. Averages out at scale.

Use when: stateless services at large scale
✓ Surprisingly effective — law of large numbers

Least Response Time

route → fastest responding server

Combines active connections + response time to pick best server.

Use when: latency is the primary concern
✓ Advanced — supported by Nginx Plus, HAProxy

API Gateway

Infrastructure

An API Gateway is a smart reverse proxy with business logic. It sits between the load balancer and your microservices and handles cross-cutting concerns so every service doesn't have to implement them individually.

What an API Gateway Adds vs a Plain Reverse Proxy

Authentication & authorisation

Validates JWT tokens, API keys, OAuth flows before the request reaches your service. Centralised — no auth code in each service.

Rate limiting

1,000 requests/min per API key. Protects backends from abuse without any application code.

Request / response transformation

Rename headers, reshape JSON body between client and service. Useful for versioning APIs.

Routing by content

Send /api/v1 to old service, /api/v2 to new service. Route by header, path, method.

Observability

Log every API call with latency, status code, API key, and payload size. Single place for all API metrics.

Circuit breaking

If a downstream service is slow or failing, stop sending it traffic and return a fallback. Prevents cascading failures.

Real-world Production Stack

# The full stack in a typical cloud deployment

User
  ↓  DNS resolves to LB IP
AWS ALB          # distributes across nodes, health checks, SSL termination
  ↓
API Gateway      # Kong / AWS API GW — auth, rate limit, route by path
  ↓         ↓         ↓         ↓
User svc  Order svc  Payment svc  Notify svc
/api/users  /api/orders  /api/payments  /api/notify
Note on collapsing layers

These layers often collapse in practice. Kong is both a reverse proxy and an API gateway. Nginx can be an LB, reverse proxy, and basic API gateway simultaneously. AWS ALB + API Gateway is the most common explicit split in cloud deployments. Don't over-engineer — add layers only when you need what they provide.

DNS Load Balancing vs Traditional Load Balancing

Infrastructure

DNS LB is blunt and slow. Traditional LB is precise and instant. They solve the same problem at different scales and with very different trade-offs.

DNS load balancingTraditional load balancer
MechanismMultiple A records for same domainDedicated process routes each connection
Health checksNone — no awareness of dead serversActive checks every 5–30 seconds
Failover speedAs slow as your TTL (minutes to hours)Seconds — 2–3 failed health checks
AlgorithmsRound robin onlyAll algorithms
Session stickinessImpossibleSupported via cookie or IP hash
Traffic splitApproximate — TTL-limitedPrecise — exact percentages
CostFree (just DNS records)Hourly cost on cloud
Best useGeo-routing across regionsEverything within a region

How They Work Together

Production systems use both. DNS LB handles global, inter-region routing. Traditional LB handles precise intra-region distribution.

# User in Chennai
DNS (GeoDNS)    → routes to ap-south-1 (Mumbai region) based on geography
AWS ALB         → distributes across 3 instances in Mumbai with health checks
Instances       → scale up/down freely behind the ALB

# User in London
DNS (GeoDNS)    → routes to eu-west-2 (London region)
AWS ALB         → distributes across instances in London

HTTP vs HTTPS

Protocol

HTTP (port 80)

  • Plaintext — anyone on the network can read it
  • No encryption — ISP, router, attacker can intercept
  • No identity verification of server
  • Man-in-the-middle attacks trivially possible
  • Modern browsers show "Not Secure" warning

HTTPS (port 443)

  • TLS-encrypted — ciphertext in transit
  • Server identity verified via SSL certificate
  • ISP can see you visited a domain — not the content
  • Certificate issued by trusted Certificate Authority
  • Required for PWAs, service workers, modern APIs

The TLS Handshake — How HTTPS Establishes Trust

Before any encrypted data flows, the client and server run a handshake to agree on a cipher, verify the server's identity via its certificate, and derive a shared symmetric key. Read it top to bottom.

SSL Termination at the Reverse Proxy

In production, HTTPS is typically terminated at the reverse proxy or load balancer. The connection between the LB and your backend services can be plain HTTP on the internal private network. This simplifies certificate management — one certificate at the edge, not on every instance.

Never Do This

Never serve sensitive production traffic over plain HTTP. Always use HTTPS. Free certificates are available via Let's Encrypt and are automatically managed by Cloudflare, AWS ACM, and Caddy.

HTTP/1.1 vs HTTP/2 vs HTTP/3

Protocol

Same concept (request-response over the web) — radically different plumbing underneath. Each generation solved the bottlenecks of the previous one. Browsers auto-negotiate the best version the server supports.

HTTP/1.1HTTP/2HTTP/3
Released199720152022
AdoptionStill common~65% of sites~30% and growing
TransportTCPTCPQUIC (over UDP)
MultiplexingNo — one request at a time per connectionYes — parallel streams on one TCPYes — independent QUIC streams
Head-of-line blockingYes — TCP-levelPartially fixed (still TCP HoLB)Eliminated — QUIC streams are independent
Connection setup1–2 RTT (TCP + TLS)1–2 RTT0–1 RTT (0-RTT on reconnect)
Server pushNoYes (largely deprecated)No
Connection migrationNoNoYes — WiFi → 4G seamlessly
Header compressionNoHPACKQPACK

When to Use Each

HTTP/1.1

Simple internal service-to-service APIs. Legacy systems where you control both ends. When you need maximum compatibility.

HTTP/2

Default choice for all public-facing APIs and websites today. Default in Nginx, AWS ALB, and most cloud infrastructure. No extra work needed.

HTTP/3

High-performance apps targeting mobile users. Video streaming (YouTube, Netflix). Fintech. Any high-latency or lossy network environment.

The Head-of-Line Blocking Problem

In HTTP/1.1, if one request stalls (e.g. a slow image), every subsequent request waits behind it on that TCP connection — like a checkout queue where one slow customer blocks everyone. HTTP/2 fixed this at the HTTP layer with multiplexing. HTTP/3 fixed it completely at the transport layer by replacing TCP with QUIC — each stream is independent, so a stalled stream doesn't block others.

Failure Scenarios

Advanced

Understanding what happens when DNS or the load balancer goes down is critical. The honest answer: if the entry point is gone with no fallback, the request fails. System design's goal is making this vanishingly unlikely.

Scenario A — DNS is Down

The request never gets an IP. The browser shows ERR_NAME_NOT_RESOLVED. No connection is even attempted. However: if the user visited recently and the browser's DNS cache hasn't expired, the browser uses the cached IP and bypasses DNS entirely. New visitors are blocked; returning visitors (within TTL) are fine.

Scenario B — Load Balancer is Down

DNS resolved successfully. The request reaches the correct IP. But nobody answers — the user gets a 502 Bad Gateway or connection timeout. In practice, cloud LBs (AWS ALB, GCP LB) run across multiple nodes and AZs, making a complete LB failure extremely rare. A single node dying is transparent.

Protections Against These Scenarios

ProtectionWhat it covers
Anycast DNS (Cloudflare/Route53)Single DNS node failure — invisible to users
Two independent DNS providersOne DNS provider's complete outage
Low TTL on health-check failover recordsRegional LB failure — reroutes in 10–60 seconds
High TTL on stable recordsDNS downtime — cached answers keep existing users connected
Active-active multi-regionFull regional outage — traffic shifts automatically
Client-side retry with exponential backoffTransient blips — app retries before showing user an error

Disaster Recovery

Advanced

RTO vs RPO

RTO — Recovery Time Objective

How long can your app be down before it causes unacceptable business impact? e.g. "We can tolerate 30 seconds of downtime." This drives how fast your failover must be.

RPO — Recovery Point Objective

How much data loss can you tolerate? e.g. "We can lose at most 5 seconds of transactions." This drives how frequently you replicate data.

The 4 Disaster Recovery Strategies

Backup & Restore

RTO: hours
  • Cheapest option
  • Snapshots to S3/GCS
  • Restore from scratch on disaster
  • Acceptable for: internal tools, blogs, non-critical apps

Pilot Light

RTO: 10–30 min
  • Core infra always on in DR region
  • DB replicating live
  • App servers OFF (scale up on disaster)
  • Acceptable for: mid-size SaaS, B2B

Warm Standby

RTO: 1–5 min
  • Scaled-down copy running in DR region
  • Handles small traffic load
  • Scale to full capacity on disaster
  • Acceptable for: e-commerce, fintech, healthcare

Active-Active

RTO: ~0 seconds
  • All regions live and serving traffic
  • GeoDNS routes to nearest region
  • Region drops = instant failover
  • Acceptable for: Netflix, Uber, banking, exchanges

How DNS Becomes the Traffic Controller

Route53 and Cloudflare run health checks against your endpoints every 10–30 seconds. When a region fails, they automatically stop returning its IP and start returning the DR region's IP. TTL on failover records is deliberately set to 10–60 seconds so the world picks up the change almost instantly.

# Normal state
myapp.com  →  PRIMARY    54.10.0.1  (Mumbai)    ✓ healthy
myapp.com  →  SECONDARY  13.20.0.2  (Singapore) ✓ standby

# Mumbai goes down — Route53 detects within 30s
myapp.com  →  SECONDARY  13.20.0.2  (Singapore) ✓ now active
# Automatic — no human intervention needed
The Hardest Problem

Routing traffic to a different region is easy. Keeping databases in sync across regions is the real engineering challenge. Solutions: CockroachDB, AWS Aurora Global, DynamoDB Global Tables, Cassandra multi-region. Trade-off: faster writes (eventual consistency) vs guaranteed sync (strong consistency, higher latency).

Real-world Incidents

Advanced

The best way to understand failure modes is to study real outages. Even the largest companies go down — the goal is fast recovery, not zero downtime forever.

Facebook — October 2021 (6 hours down)

A BGP misconfiguration caused Facebook to withdraw their own DNS routes from the internet. Their DNS became completely unreachable globally. Even internal engineers couldn't log in to fix it because their VPN used the same DNS. WhatsApp, Instagram, and Facebook were all simultaneously unavailable. Lesson: DNS is not a commodity — it's critical infrastructure.

Dyn DNS — October 2016 (several hours)

A massive DDoS attack hit Dyn, a major DNS provider. Twitter, Netflix, Reddit, GitHub, Spotify, and dozens of other sites went down for hours — not because those sites failed, but because Dyn couldn't resolve their domain names. The sites themselves were perfectly healthy. Lesson: using a single DNS provider is a single point of failure at the internet level.

AWS us-east-1 — Multiple incidents

AWS's primary US region has had several significant outages. Companies with multi-region setups (active-active or warm standby) experienced little to no user impact. Companies that deployed only to us-east-1 went fully down. Lesson: never rely on a single region for production workloads that have availability SLAs.
